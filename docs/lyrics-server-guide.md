# 가사 서버 사용 가이드

기기마다 따로 놀던 가사·번역 캐시를 서버 한 대에 모아, **한 번 찾은 가사는 모든 기기가 함께 쓰도록**
하는 기능이다. PC에서 들은 곡을 폰에서 다시 들어도 제공자 검색과 유료 번역을 반복하지 않는다.

- 운영자용 설치·배포: `src/Musebase.Server/deploy/README.md`
- 백업·복구·다른 서버로 이전: `src/Musebase.Server/deploy/MIGRATION.md`
- HTTP 계약(개발자용): `contracts/lyrics-api.md`

---

## 1. 어떻게 동작하나

```
로컬 캐시 히트  →  (없으면) 서버 조회  →  (없으면) 제공자 검색 → 번역 → 로컬·서버 양쪽 저장
```

핵심은 **각 기기의 로컬 캐시에 없는 곡만 서버로 간다**는 점이다. 같은 곡을 반복 재생해도 서버 조회 수는
늘지 않는다. 서버에서 받은 가사는 로컬 캐시로 승격되므로, 다음부터는 서버 없이도(오프라인에서도) 뜬다.

가사 캐시에는 번역이 함께 박혀 있어서, **곡을 공유하면 번역도 함께 공유**된다.

서버는 **있으면 좋은 것**이지 필수가 아니다. 주소를 넣지 않으면 예전과 똑같이 동작하고,
서버가 꺼져 있거나 테일넷 밖이면 조용히 기존 방식(제공자 검색)으로 내려간다 — 기능이 줄지 않는다.

## 2. 앱에 연결하기

준비물은 두 가지다.

| | |
|---|---|
| 주소 | `https://oracle.oryx-skink.ts.net` (테일넷 안에서만 접속됨) |
| 토큰 | 서버에서 `sudo grep MUSEBASE_TOKEN /etc/musebase/server.env` |

**Windows** — 트레이 → 설정 → **[소스] 탭** → "개인 가사 서버"에 주소와 토큰 입력 → 저장
**Android** — 설정 → **[재생 소스] 탭** 아래쪽 "개인 가사 서버"에 같은 값 입력 → 저장

둘 다 **저장 즉시 반영**된다(재시작 불필요). Windows는 토큰을 DPAPI로 암호화해 저장하고,
Android는 앱 내부 저장소에 둔다(디스크 암호화는 아님 — 테일넷 안에서만 쓰는 개인 토큰이라는 전제).

> **Android는 반드시 `https://` 주소**를 쓴다. 평문 http는 시스템이 차단한다.
> 그리고 Tailscale이 켜져 있어야 접속된다 — 꺼져 있으면 그냥 예전처럼 동작한다.

### 잘 되고 있는지 보는 법

- 관리자 페이지(아래)의 "최근 조회"에 내 기기 이름과 함께 기록이 쌓인다.
- Windows 로그(`%LOCALAPPDATA%\Musebase\app.log`)에 `[server] 히트: …`가 찍힌다.
- 확실히 시험하려면 로컬 캐시에서 그 곡을 지우고(또는 다른 기기에서) 재생해 본다.

## 3. 관리자 페이지

브라우저로 연다 — `https://oracle.oryx-skink.ts.net/admin?token=<토큰>`
한 번 열면 쿠키가 저장되고 주소창이 `/admin`으로 정리된다(30일 유지, `/admin/logout`으로 해제).
테일넷 안에서만 열린다.

### 대시보드에서 보는 것

| 타일 | 의미 |
|---|---|
| 마지막 조회 | "3분 전 · home-pc" — 서버가 살아 쓰이고 있는지 한눈에 |
| 오늘 조회 | 오늘 몇 곡이 서버로 왔고 그중 몇 개가 히트였는지 |
| 히트율 (7일) | 서버에 있어서 검색을 아낀 비율 |
| 보관 중인 가사 | 곡 수 · 번역 있는 곡 수 · DB 크기 |

그 아래로:

- **최근 조회** — 히트(초록) / 히트(느슨, 노랑) / 미스(빨강)와 기기 이름
- **미스 상위** — 서버에 없어서 각 기기가 직접 찾아야 했던 곡. **채울 후보 목록**이다
- **기기별 · 일별** — 어느 기기가 얼마나 쓰는지, 날짜별 히트율
- **번역 없는 곡** — 나중에 일괄 번역할 대상
- **표기 차이로 갈린 곡 후보** — 같은 곡이 두 벌로 저장됐는지 점검
- **진단** — 실제로 들어오는 요청 헤더와 서버 상태(업타임·메모리·디스크)

> "히트(느슨)"는 표기가 달라도 같은 곡으로 맞춘 경우다. 예: Windows는 아티스트를
> `MGMT — Oracular Spectacular`로, Android는 `MGMT`로 보고하는데 둘을 같은 곡으로 본다.

### 가사 검색·열람·수정

**가사 검색** 탭에서 제목·아티스트로 찾고, 곡을 누르면 **시간 · 원문 · 번역** 3열로 볼 수 있다.
번역 언어 선택, 타임태그 숨기기, 원문(.lrc) 내려받기가 된다.

- **편집** — 가사를 고쳐 저장하면 `origin=user`가 되어, 이후 어느 기기의 자동 검색도 이 가사를
  덮어쓰지 못한다. 틀린 가사를 한 번 고치면 모든 기기에 적용된다.
- **삭제** — 지우면 다음에 어느 기기든 그 곡을 재생할 때 다시 찾아서 새로 채운다.
  (잘못된 가사가 박혔을 때 가장 빠른 해결책)

## 4. 잘 안 될 때

**곡이 아예 인식되지 않는다**
1. 트레이 → 재생 소스가 특정 앱으로 **고정**돼 있지 않은지 본다. 고정하면 그 앱만 따라간다.
   상태 표시줄에 "…대기 중 — 고정해 둔 플레이어가 실행 중이 아닙니다"가 뜨면 이 경우다.
2. 설정 [소스]의 **선호 음악 앱**에 체크가 하나라도 있으면 그 앱들만 인식한다. 진단할 때는 전부 해제한다.
3. 그래도 안 되면 **그 플레이어가 Windows에 재생 정보를 알리지 않는 것**이다.
   볼륨 키를 눌렀을 때 곡 정보 오버레이가 뜨지 않거나 잠금화면에 곡이 안 나오면 확실하다.
   (실제 사례: Microsoft Store 버전 MusicBee는 이를 발행하지 않아 어떤 앱도 감지할 수 없었다.
   일반 설치 버전 + SMTC 플러그인으로 해결)

**서버에서 가사를 못 받아온다**
- Tailscale이 켜져 있는지 확인한다(폰은 특히).
- 서버가 죽어 있으면 조회 2.5초 뒤 평소대로 검색으로 넘어가고, 이후 60초 동안은 서버를 건너뛴다
  (매번 기다리지 않도록). 즉 **느려지지 않는다.**
- 관리자 페이지가 열리는지로 서버 생사를 확인할 수 있다.

**같은 곡이 두 벌로 저장된 것 같다**
관리자 페이지의 "표기 차이로 갈린 곡 후보"를 본다. 필요하면 한쪽을 지운다.

## 5. 백업

서버가 매일 새벽 4시에 자동으로 백업한다 — 스냅샷을 뜬 뒤 **무결성 검사를 통과한 것만** 압축해
14일간 보관한다. 별도로 할 일은 없다.

- 수동 1회: `sudo /usr/local/bin/musebase-backup`
- 다른 기계에도 한 부 보내려면 서버 설정에 `MUSEBASE_BACKUP_REMOTE=user@host:/path` 한 줄
- 복구·이전 절차: `src/Musebase.Server/deploy/MIGRATION.md`

## 6. 프라이버시

- 가사와 번역, 그리고 **조회 기록(어느 기기가 언제 어떤 곡을 찾았는지)** 이 서버에 쌓인다.
  사실상 청취 이력이므로, 서버는 테일넷 안에서만 접근 가능하게 두었다(공개 포트 없음).
- 조회 기록은 **90일 후 자동 삭제**된다. 남기고 싶지 않으면 서버 설정에 `MUSEBASE_LOG_LOOKUPS=0`.
- 앱은 서버 주소를 넣지 않으면 아무것도 서버로 보내지 않는다(기본값은 사용 안 함).
